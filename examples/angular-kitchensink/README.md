# Angular kitchen sink

An Angular application with server-rendered public content, oidc-spa authentication, an application user model, and client-rendered protected routes. The tooling follows the standalone, zoneless project generated by [Angular CLI](https://angular.dev/tools/cli/setup-local) 22.1.7, including its Vitest test runner.

## Getting started

Use Node.js 24.15+ (24.x LTS). Angular also supports Node.js 22.22.3+ (22.x) and 26+.

```bash
npx gitpick keycloakify/oidc-spa/tree/main/examples/angular-kitchensink start-oidc
cd start-oidc
npm install
npm start
```

Open http://localhost:4200. Yarn and pnpm work too: use `yarn install` / `yarn start` or `pnpm install` / `pnpm start`.

Configure the issuer and client in `public/oidc-config.json`. The application loads this configuration at startup with `HttpClient`. Define the application user in `src/app/services/oidc.service.ts` with `oidcSpa.withUser()`. See the [user abstraction documentation](https://docs.oidc-spa.dev/features/user).

`src/main.ts` runs `oidcEarlyInit()` before dynamically loading Angular through `src/main.lazy.ts`. Keep this browser-only boundary so OIDC callback handling can finish before the application boots. The server bootstraps Angular separately through `src/main.server.ts`.

This example also demonstrates non-blocking initialization, per-request bearer-token configuration, and an admin-only route. See [the Angular user abstraction guide](USER_ABSTRACTION.md) for details.

To develop with a mocked, signed-in user and no identity provider:

```bash
npm start -- --configuration mock
```

The mock configuration replaces `src/environments/environment.ts` with `environment.mock.ts`. Mock development uses the normal development build settings.

## Commands

- `npm start` — start the development server with live reload.
- `npm run build` — create a production build in `dist/angular/browser` and `dist/angular/server`.
- `npm run serve:ssr:angular` — serve the production build at http://localhost:4000 (`PORT` overrides the port).
- `npm run watch` — rebuild the development output when files change.
- `npm test` — run Vitest in watch mode.
- `npm test -- --watch=false` — run the tests once, without a browser or identity provider.
- `npm run ng -- generate component my-component` — generate an Angular component.

## Server rendering

The setup follows a fresh `ng new --ssr` project from Angular CLI 22.1.7. `src/app/app.routes.server.ts` selects the rendering mode:

- `/` renders on the server, including public content and authentication placeholders.
- `/protected` and `/admin-only` use `RenderMode.Client`. A direct visit loads the application in the browser, where the login guard can establish authentication.

`provideClientHydration()` lets Angular reuse the public page's server-rendered HTML. Authentication-dependent UI uses `@defer (when oidc.prInitialized | async)`: initialization stays pending on the server and completes in the browser. The public todo request is also deferred because its optional bearer token depends on the authentication state.

Routes that use `enforceLoginGuard` must use `RenderMode.Client`; the guard explains this if a protected route is accidentally configured for SSR.

To preview a production build without an identity provider:

```bash
npm run build -- --configuration production,mock
npm run serve:ssr:angular
```

For deployment, run the generated Node server and deploy both output folders. Add your deployment hostname to `projects.angular.architect.build.options.security.allowedHosts` in `angular.json` before building, following [Angular's host validation guidance](https://angular.dev/guide/ssr). This example now requires a server runtime for request-time SSR; copying only the browser folder to a static host does not provide that behavior.

Direct dependencies are pinned to compatible versions from the current Angular CLI setup; `oidc-spa` stays on `latest`. No lockfile or package manager is imposed on users. `pnpm-workspace.yaml` allows the native build scripts used by Angular CLI (pnpm 10.26+). Transitive dependencies can still change between fresh installations.
